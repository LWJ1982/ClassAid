# Role-personalized dashboards, second domain, and instructor preview mode

This change adds a second domain (Computer Science with a sorting algorithms module), expands the demo user pool to 7 accounts, introduces domain-filtered dashboards for learners and module-filtered dashboards for instructors, an admin user management panel (add/remove), and an instructor preview mode that simulates the learner journey without persisting data. The approach keeps everything in demo mode with localStorage persistence and React Context, avoiding any backend changes.

Watch for: The learner flow beyond the dashboard is still hardcoded to module-1 data (confirmed) — CS learners will see the correct module cards but entering any module drops them into electrical engineering content. The `previewResultStore` module-level mutable singleton creates a stale-state coupling between sibling components that breaks under concurrent renders or React strict mode (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The personalization model filters at the dashboard level — learners see only modules matching their `domainId`, instructors see only modules matching their `ownerId`. But the learner journey components below the dashboard (module overview, guided activity, assessment) still import module-1 data directly, so the personalization is incomplete for CS-domain learners.

The instructor preview mode uses a fully isolated component tree that avoids mutating global learner state. However, results pass between the assessment and report steps via a module-level mutable object (`previewResultStore`) that is written during render, making it fragile under strict mode and never cleared between sessions.

The admin user management persists to localStorage and prevents self-removal through the UI, but `removeUser` at the context level has no guard against removing the currently-selected demo user, which would cause a silent role switch.

## Learner flow hardcoded below the dashboard

Clicking "Start Preparation" on any card calls the same `onStart` callback which navigates to `ModuleOverview` — a component that imports `learningModule` (the electrical engineering module) at the module level:

```typescript
// src/components/learner/module-overview.tsx line 3
import { learningModule as module, domain, moduleVersion, objectives, competencies } from "@/lib/data/seed";
```

`Assessment` and `GuidedActivity` consume `moduleConfig` from context, which `getInitialConfig()` builds exclusively from module-1 seed data (`seedCompetencies`, `seedQuestions`, `seedActivities`, `seedCheckpoints`). A learner assigned to `domain-2` will see the correct dashboard but get the wrong content for every subsequent screen.

## Preview result passing via module-level store

`PreviewAssessment` and `PreviewReport` are sibling components rendered by `LearnerPreview` based on a step state variable. The assessment results are shared through:

```typescript
// src/components/instructor/preview-assessment.tsx (bottom of file)
export const previewResultStore: { result: ReadinessResult | null; answers: AttemptAnswer[] } = {
  result: null,
  answers: [],
};
```

This mutable singleton is written during render (inside the component body, outside useEffect). React strict mode in development double-invokes render functions, and any future concurrent rendering could produce stale or crossed reads. The store is never cleared between preview sessions — if an instructor exits preview and re-enters, the previous result may flash briefly before the new assessment overwrites it.

## User management state boundaries

`removeUser` at the context level is an unguarded filter:

```typescript
const removeUser = useCallback((userId: string) => {
  setUsers((prev) => prev.filter((u) => u.id !== userId));
}, []);
```

If the removed user is the one referenced by `selectedDemoUserId`, the `currentUser` derivation falls through to `users[0]`, which may be an entirely different role. The UI prevents admins from removing themselves, but doesn't protect against removing the currently-active demo user when viewing as a non-admin.

`addUser` performs no duplicate-email check and generates IDs with `Date.now()`.

## Test coverage gap

The personalization logic (domain filtering, ownership filtering) and the `previewResultStore` coupling have no unit test coverage. The domain-filtering gap in the learner flow would be caught by a test that asserts a CS learner sees CS content after clicking "Start Preparation."
