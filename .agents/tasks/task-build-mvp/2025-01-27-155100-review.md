# Supabase + Groq MVP — v3 final review

All ten issues from the prior two reviews have been resolved. JWT validation via `extractUser`, role-based authorization via `requireRole`, shared readiness engine usage, the partial-unique idempotency index, partial submission rejection before the engine call, six-category keyword classification, real database queries in insights, content-type rejection for non-text uploads, and auth-aware GET endpoint filtering are all in place and correctly implemented.

Demo mode remains a deliberate bypass — when no Bearer token is present, any `learnerId` value in the request body is trusted without verification (confirmed, documented trade-off for MVP).

**Verdict**: APPROVED

## High-level view

The security boundary between production and demo modes hinges on the presence of an `Authorization` header. When present, `extractUser` validates the JWT and extracts identity/role from Supabase Auth. When absent, the body-supplied fallback ID is accepted as-is. This two-tiered model is reasonable for an MVP where demo mode is explicitly opted into by not configuring Supabase Auth credentials.

Role-based authorization is consistently applied on all write operations and on the sensitive GET endpoint (`insights`). The `modules` GET endpoint is auth-aware with graceful degradation. The one gap is `checkpoints` GET, which bypasses auth entirely and leaks correct answers for checkpoint questions to any anonymous caller.

The assessment scoring pipeline is a clean chain: Zod validation → auth → idempotency app-check → load questions/competencies → validate completeness (400 before engine) → shared `calculateReadiness` engine → persist with unique-index safety net. The TOCTOU concern from v2 is closed by the partial unique index catching concurrent duplicates at the database level.

Integration tests (HTTP handlers, auth flow, RAG pipeline end-to-end) remain absent, which is typical for an MVP but worth noting for the next iteration.

## Unauthenticated checkpoint data exposure

The `onRequestGet` handler in `functions/api/checkpoints.ts` imports `extractUser` and `requireRole` but only uses them in `onRequestPatch`. The GET handler queries with the service-role client (`select('*, activities(title, sequence)')`) and returns the full question objects including `correct_answer`, `explanation`, and `failure_hint` to any caller without authentication.

For checkpoint questions (comprehension gates during guided activities), this means a learner could bypass the checkpoint by fetching the answers directly:

```
GET /api/checkpoints?moduleId=<id>
// Returns: [{ question_text, correct_answer, ... }]
```

The fix is straightforward — mirror the PATCH handler's auth pattern:

```typescript
const user = await extractUser(request, supabase);
if (!user || !requireRole(user, ['instructor', 'admin'])) {
  return Response.json({ error: 'Forbidden' }, { status: 403 });
}
```

If learners need to fetch their own checkpoint questions (without answers), a separate filtered query that excludes `correct_answer` would be needed.
