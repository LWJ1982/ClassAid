# Supabase + Groq MVP with v1 review fixes applied

The six issues from the first review have all been addressed: JWT validation now happens via a shared `extractUser` helper using Supabase `auth.getUser(token)`, the assessment function imports and calls the shared `calculateReadiness` engine rather than reimplementing it, duplicate submissions are blocked with a `learner+module+version+scored` check returning 409, chat classification uses keyword-based matching across all six categories, insights queries the database instead of returning literals, and upload rejects non-text content types explicitly.

Watch for: Partial answer submissions produce a misleading 503 instead of a 400 because the engine's "incomplete attempt" exception is caught by the outer error handler (confirmed). No role-based authorization exists at the API layer — any authenticated user can generate questions, approve checkpoints, or view instructor insights without being an instructor (confirmed). The `insights` and `modules` GET endpoints don't call `extractUser` at all, making them accessible without any authentication when using the service-role client (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The `extractUser` helper closes the identity trust gap for the five POST/PATCH endpoints that use it, but the two GET endpoints (`modules`, `insights`) skip it entirely. Since these use the service-role client (which bypasses RLS), any unauthenticated caller can read all modules regardless of publication status and all instructor analytics.

The shared engine integration eliminates the scoring duplication, and the idempotency check prevents duplicate submissions. One gap remains: if a learner submits fewer answers than there are approved questions, the engine throws "incomplete attempt" and the function returns a generic 503 rather than a descriptive 400.

Authorization is identity-only, not role-based. Once a user is authenticated (or provides an ID in demo mode), they can call any endpoint regardless of their role. A learner can POST to `/api/generate` to trigger question generation or PATCH `/api/checkpoints` to approve questions. The security steering file requires instructor-only access for these operations.

1. **Partial submission returns 503 instead of 400** — When a learner submits fewer answers than there are approved questions, `calculateReadiness` throws "Incomplete attempt" which the outer catch converts to a 503. Add a length check before calling the engine, or catch the specific error and return 400 with the engine's message.
2. **No role-based authorization on write endpoints** — `generate`, `upload`, `checkpoints` (PATCH), and `insights` all perform instructor/admin operations but don't verify the caller's role. Any authenticated learner can generate questions, approve checkpoints, upload documents, or view analytics. Check `user_metadata.role` from the JWT or query the users table.
3. **GET endpoints bypass authentication entirely** — `/api/modules` and `/api/insights` don't call `extractUser`. Since the service-role client bypasses RLS, these return all data to any caller including unauthenticated requests. At minimum, add auth validation; ideally, restrict insights to instructors.
4. **Idempotency check is not atomic** — The "check then insert" pattern for duplicate submission has a TOCTOU window. Two simultaneous requests could both pass the `.maybeSingle()` check before either inserts. Add a unique constraint on `(learner_id, module_id, module_version)` where `status = 'scored'`, or use a Supabase RPC with serializable isolation.

## Partial answer handling gap

The assessment endpoint validates that each submitted `questionId` exists in the approved set, but never checks that all approved questions have a corresponding answer. The readiness engine enforces completeness (`answers.length !== questions.length` throws), but the error surfaces as an untyped exception in the outer catch block:

```typescript
const result = calculateReadiness({
  attemptId,
  questions: engineQuestions,  // all approved questions
  answers: engineAnswers,      // only submitted answers
  ...
});
// If engineAnswers.length < engineQuestions.length, throws:
// "Incomplete attempt: expected N answers, received M"
// Caught by outer try-catch -> 503 "Service temporarily unavailable"
```

A learner submitting 3 of 10 answers gets "Service temporarily unavailable" rather than "Incomplete attempt: expected 10 answers, received 3." The fix is either a pre-check (`if (answers.length !== (questions || []).length) return 400`) or catching the engine error specifically and returning its message with status 400.

## Missing role-based authorization

The `extractUser` helper establishes *who* the caller is, but none of the endpoints check *what role* they have. In production with authenticated users, a learner could:

1. Call `POST /api/generate` with any moduleId to trigger LLM question generation (and incur Groq API costs)
2. Call `PATCH /api/checkpoints` with `action: "approve"` to approve questions — bypassing the instructor review gate entirely
3. Call `GET /api/insights?moduleId=...` to see other learners' scores and readiness distribution

The `user_metadata.role` is available from the Supabase JWT (`data.user.user_metadata.role` in the `getUser` response). Adding a role field to `AuthenticatedUser` and checking it in the relevant handlers would close this gap.

## Unauthenticated GET endpoints

`/api/modules` and `/api/insights` don't import or call `extractUser`. They use the service-role client directly, which bypasses all RLS policies. Anyone who can reach the Pages Function URL can:

- `GET /api/modules` — returns all modules (draft, published, archived) for all owners
- `GET /api/insights?moduleId=X` — returns completion rates and readiness distribution

The modules endpoint applies a `status` filter if provided, but doesn't enforce that draft/archived modules are hidden from non-owners. Since this is a service-role query, the RLS policy `modules_read_published` has no effect.

## Idempotency TOCTOU window

The duplicate submission check queries for existing scored attempts, then (if none found) inserts a new one. Under concurrent requests:

```
Request A: SELECT ... WHERE learner_id=X, module_id=Y, status='scored' -> 0 rows
Request B: SELECT ... WHERE learner_id=X, module_id=Y, status='scored' -> 0 rows
Request A: INSERT INTO attempts ...
Request B: INSERT INTO attempts ...  (both succeed, duplicate)
```

A partial unique index (`CREATE UNIQUE INDEX ON attempts(learner_id, module_id, module_version) WHERE status = 'scored'`) would make the second insert fail at the database level. The function could then catch the unique violation error (code `23505`) and return 409.

## Test coverage gaps

The 56 tests cover the readiness engine, Groq client, and Zod schemas. No test exercises the HTTP handler layer, the `extractUser` helper, or the assessment orchestration (DB row mapping + engine call + persistence). The data-mapping layer between Supabase row format and engine domain types is untested — a field name mismatch (e.g., `q.competency_id` vs the domain type's `competencyId`) would not be caught until runtime.

Not tested: `extractUser` JWT validation, assessment partial-submission error path, chat RAG pipeline, upload chunking + embedding flow, generate question validation pipeline.
