# Supabase + Groq MVP: schema, functions, auth, tests, and deployment scaffold

Class AId's backend has been rewritten from Cloudflare D1/R2/Vectorize to Supabase PostgreSQL (pgvector, Auth, Storage) + Groq (LLM) + Workers AI (embeddings only). The change delivers the full database schema with RLS, rewrites all 7 Pages Functions to use the new stack, adds Supabase Auth with demo-mode fallback, provides 56 unit tests, and includes deployment docs plus an AWS CDK migration scaffold. The architecture boundary (browser talks only to Pages Functions, never to Groq/Supabase service-role) is maintained.

Watch for: Pages Functions accept `learnerId` from the request body without JWT validation, meaning any caller can impersonate any user (confirmed). The `insights` endpoint hardcodes assigned/started counts (confirmed). Assessment scoring doesn't reject duplicate submissions for the same module+learner, violating the idempotency requirement (likely). Chat `category` is always hardcoded to `'CONCEPT'` regardless of actual question classification (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

RLS policies cover all 15 tables and correctly separate learner, instructor, and admin access. But the Pages Functions bypass RLS entirely via the service-role key and don't validate the caller's identity from the JWT — so the RLS policies only protect against direct client-side Supabase queries (which, by design, only happens for auth).

The assessment scoring path is deterministic and server-side; AI cannot influence pass/fail. However, the scoring logic in the Pages Function (`functions/api/assessments.ts`) is a reimplementation of the readiness engine (`src/lib/engine/readiness-engine.ts`) rather than a call to it. The 19 engine tests don't exercise the production code path, and the two implementations have subtly different threshold boundaries.

Auth integration sets a Bearer token on all API requests from the client. The Pages Functions never extract or verify that token, making the auth header decorative at the server layer.

Question generation correctly validates AI output structure and discards malformed JSON, storing valid output as `auto_generated` (never `approved`). The chat endpoint constructs citations from retrieval metadata rather than LLM output, which prevents citation hallucination.

1. **No server-side JWT validation** — Pages Functions trust `learnerId`/`uploadedBy`/`requestedBy` from the request body. Extract identity from the Bearer token instead of accepting caller-supplied IDs.
2. **Scoring logic duplication** — `functions/api/assessments.ts` reimplements the readiness engine instead of calling `calculateReadiness`. The two implementations may drift; a single source of truth is needed.
3. **No assessment idempotency** — Nothing prevents a learner from submitting the same assessment multiple times. Add a uniqueness constraint or check before inserting.
4. **Chat category always CONCEPT** — The response always returns `category: 'CONCEPT'` with no classification logic. Either implement question classification or remove the field from the contract.
5. **Insights hardcoded counts** — `assigned: 30, started: 27` are literal numbers, not database queries. These metrics are meaningless in production.
6. **Upload chunking is text-only** — `file.text()` will produce garbage for PDFs, DOCX, and other binary formats. The upload endpoint needs format-aware extraction or explicit rejection of non-text files.

## Server-side identity trust gap

Every Pages Function that writes data accepts the actor identity from the request body: `learnerId` in assessments and chat, `uploadedBy` in upload, `requestedBy` in generate. The auth-provider on the client sets a Bearer token via `apiClient.setAuthToken()`, and the token is sent in the `Authorization` header. But no function reads this header.

```typescript
// functions/api/assessments.ts
const { moduleId, learnerId, answers } = parsed.data;
// learnerId is used directly to persist the attempt — no JWT verification
```

The FEAT-004 findings explicitly note: "Step 8 (Pages Functions JWT validation) was not implemented." A malicious client can submit assessments, upload files, or generate questions on behalf of any user by setting an arbitrary ID in the body. The RLS policies provide no defense because the service-role client bypasses them entirely.

The fix involves extracting the user from the JWT (Supabase provides `supabase.auth.getUser(token)` on the server) and using that identity instead of the body field.

## Assessment scoring duplication

The readiness engine at `src/lib/engine/readiness-engine.ts` has 19 passing tests covering all boundary conditions from the testing steering file. The assessment Pages Function reimplements the same logic inline with subtly different threshold boundaries:

- Engine: uses `overallThreshold * 0.75` as the boundary between `REVIEW_REQUIRED` and `FURTHER_PREPARATION`
- Function: uses `threshold * 0.75` for the same boundary, and additionally uses `threshold * 0.6` for mandatory-competency failures

The function's status logic:
```typescript
if (criticalFailures.length > 0) {
  status = 'REVIEW_REQUIRED';
} else if (competencyScores.some((cs) => cs.mandatory && !cs.passed)) {
  status = overallScore < threshold * 0.6 ? 'FURTHER_PREPARATION' : 'REVIEW_REQUIRED';
} else if (overallScore >= threshold) {
  status = 'READY';
} else {
  status = overallScore >= threshold * 0.75 ? 'REVIEW_REQUIRED' : 'FURTHER_PREPARATION';
}
```

Since the tests exercise only the engine module and not the function, any drift between them is invisible. The function should import and call `calculateReadiness` rather than maintaining its own copy.

## No duplicate submission prevention

The security steering file requires: "Duplicate submissions rejected (idempotency)." The assessment function generates a new `attemptId` on every call and inserts it unconditionally. There is no check for an existing scored attempt by the same learner for the same module version, and no database constraint prevents it.

## Chat response classification

The chat endpoint hardcodes `category: 'CONCEPT'` on every response. The AI boundaries steering file defines six categories (CONCEPT, PROCEDURE, COMPLIANCE, TROUBLESHOOTING, APPLICATION, OUT_OF_SCOPE). No classification logic exists — not in the system prompt, not in post-processing.

## Insights endpoint placeholder data

```typescript
return Response.json({
  moduleId: parsed.data.moduleId,
  assigned: 30,  // hardcoded
  started: 27,   // hardcoded
  completed,     // real query
  ...
});
```

`assigned` and `started` are literals. This will always show "90% started" regardless of actual enrollment.

## Upload format assumption

The upload handler calls `file.text()` to extract content for chunking. For PDF, DOCX, or other binary formats, `file.text()` returns binary gibberish. The quality gate (`textContent.trim().length < 50`) catches zero-length content but not binary noise that exceeds 50 characters.

The handler should either reject non-text content types explicitly or integrate a text extraction library for common document formats.

## Test coverage gaps

The 56 tests cover the readiness engine boundaries (19), Groq client error handling (9), and Zod validation schemas (28). All required test cases from testing.md are present for the engine.

Not tested: the Pages Functions themselves (HTTP handlers), the auth flow, embedding generation, vector search RPC, the chunking algorithm, the upload pipeline, or the generate pipeline. The production scoring path in `functions/api/assessments.ts` is untested. Integration tests (file upload -> chunks -> embeddings, RAG query -> response, assessment -> scoring -> persistence) are listed as required in testing.md but not implemented.
